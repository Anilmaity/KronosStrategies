WHY THIS FILE
-------------
Two different layers can stop Claude from running a command:

  1. permissions.allow  — classic Bash/tool allow-rules. A missing rule here
     just means Claude asks before running (or is blocked in stricter modes).

  2. autoMode.allow     — the AUTO-MODE CLASSIFIER. This is the safety layer
     that flagged the live deploys this session ("Production Deploy",
     "Production Reads", "Self-Modification"). It is SEPARATE from
     permissions.allow: even with `Bash(ssh:*)` allowed, the classifier still
     blocks an ssh command it judges to be a real-money production deploy
     unless an autoMode.allow rule authorizes it.

So: shell-shape rules go in `permissions.allow`; intent/authorization for
risky prod actions goes in `autoMode.allow` (natural-language rules; keep
"$defaults" first to inherit the built-in safety rules).

Scope note: this file lives in .claude/settings.json (committed, team-wide). If
you'd rather keep the real-money deploy authorization personal/uncommitted, put
the autoMode.allow block in .claude/settings.local.json instead (gitignored) —
arrays merge across both files.

WHAT EACH ENTRY COVERS
================================================================================

permissions.allow (shell-shape rules)
  Bash(ssh:*) / Bash(scp:*) ........ deploy + file sync to algorobos
  Bash(aws lightsail get-...password) ... fetch app-DB master password
  manage.py migrate / showmigrations .... Django migrations on the live DB
  python -m db.migrate_env_creds_to_accounts ... one-off creds migration
  -m pytest ........................ run the test suite (usually already free)
  git push / git commit ............ push branches / commit (usually free; here
                                      for stricter permission modes)

autoMode.allow (classifier authorizations — the real blockers this session)
  Entry 1: June prod rollout (existing) — DB password, migrations, backend deploy.
  Entry 2: NEW — the trading-bot deploys. This is the one that unblocks
           `docker compose build`/`up`/`--force-recreate` for challenge_xau_h4
           and telegram_trader, and editing CHALLENGE_*/DRY_RUN in the box .env.
           It explicitly covers flipping a live MetaAPI account.
  Entry 3: NEW — read-only live diagnostics (the account-information / region
           probe that was blocked while debugging the 403), with a hard
           guardrail against printing secrets.

================================================================================
WHAT IS DELIBERATELY *NOT* GRANTED (kept manual on purpose)
================================================================================
  - Dumping secrets: /proc/<pid>/environ, full container env, printing tokens.
  - `docker compose down -v` / volume deletion (could wipe the tg_session login).
  - Anything outside the algorobos host or the named compose services.
  - Editing .claude/settings.json itself (self-modification stays manual — this
    is why Claude generated this file for you to apply rather than applying it).

================================================================================
HOW TO APPLY
================================================================================
  1. Replace the contents of .claude/settings.json with the READY-TO-PASTE block
     above (or merge the new autoMode.allow entries into your existing array).
  2. Save. New tool calls pick it up; if it doesn't seem to take, open /hooks
     once or restart the session to reload settings.
  3. Then Claude can run the challenge_xau_h4 build/recreate + log checks itself
     (no `!` prefix needed).

To NARROW later: delete autoMode.allow entry 2 and/or 3 — Claude reverts to
asking/blocking on those prod actions. To keep them personal-only, move entries
2 and 3 to .claude/settings.local.json.
